# Wave 0: аудит ресурсов для Poruchik

## Решение

**RESOURCE FAIL:** добавлять на текущий VPS одновременно шлюз Poruchik и серверное ядро задач нельзя. Процессор, диск и количество индексных дескрипторов имеют достаточный резерв, но оперативная память уже испытывала реальное истощение. До Wave 1 требуется ручное увеличение оперативной памяти минимум до 4 ГиБ и повторная проверка.

Аудит был только читающим. Конфигурация сервера, контейнеры, сеть, DNS и данные не изменялись. Адреса, ключи и пользовательские идентификаторы в документ не включены.

Сумма текущего потребления контейнеров во время проверки — около 887 МиБ. Сумма их зафиксированных максимумов — около 1 445 МиБ. Сумма настроенных жёстких лимитов — 1 888 МиБ, то есть уже больше всей физической памяти VPS.

За время текущей загрузки ядро Linux трижды включало аварийное освобождение памяти: 29 августа один раз и 30 августа два раза. В этих событиях завершался процесс мониторинга Netdata. Это прямое доказательство, что свободные 644 МиБ в одном моментном замере нельзя считать безопасным запасом.

## PostgreSQL

PostgreSQL принимает соединения. Размеры баз невелики: основная база агента около 10 МиБ, база n8n около 22 МиБ. Во время проверки было 7 соединений из разрешённых 100.

Контейнер помечен `unhealthy` не из-за остановки базы, а из-за рассинхронизации эксплуатационной проверки и выданных прав. Служебная роль выполнения не имеет права запуска четырёх функций обработки напоминаний и записи ошибок, которые требует текущая проверка готовности. Файл проверки, подключённый к контейнеру, отличается от актуального файла в кодовой базе. До подключения серверного ядра задач это расхождение нужно устранить и получить состояние `healthy`.

## Сеть и границы доступа

- Из контейнерного контура наружу опубликован только HTTPS на порту 443.
- n8n доступен только через `127.0.0.1:5678`.
- SSH слушает порт 22 по IPv4 и IPv6.
- Сеть данных Docker изолирована; пересылка через Docker по умолчанию запрещена.
- В показанной конфигурации не обнаружена отдельная входная цепочка межсетевого экрана самого хоста. Перед расширением пилота необходимо отдельно подтвердить правила провайдера или настроить входной фильтр хоста; это не требует открытия внутренних портов.

## Допустимые ограничения после расширения

Для первого пилота шлюз и серверное ядро задач получают суммарно не более 512 МиБ:

| Новый процесс | Резерв памяти | Жёсткий предел | Процессор | Процессы |
|---|---:|---:|---:|---:|
| Шлюз Poruchik | 64 МиБ | 128 МиБ | 0,25 ядра | 64 |
| Серверное ядро задач | 256 МиБ | 384 МиБ | 0,75 ядра | 192 |

Для серверного ядра задач на Java: начальный размер кучи 128 МиБ, максимальный 256 МиБ. Для обоих процессов: корневая файловая система только для чтения, удаление всех лишних системных привилегий, запись только в явно выделенные каталоги.

После добавления этих процессов сумма жёстких лимитов контейнеров составит 2 400 МиБ. Поэтому минимальный безопасный тариф — **4 ГиБ физической оперативной памяти**. После изменения тарифного плана фактический `MemTotal` должен быть не меньше 3,5 ГиБ; под операционную систему, Docker, мониторинг, файловый кеш и всплески остаётся не меньше 768 МиБ. Два виртуальных ядра можно сохранить для закрытого пилота; необходимость четырёх ядер определяется только нагрузочным испытанием.

## Ручная контрольная точка перед Wave 1

1. Увеличить оперативную память VPS минимум до 4 ГиБ без изменения DNS и внешней схемы доступа.
2. После обязательной перезагрузки подтвердить фактические 4 ГиБ и повторить только читающий аудит памяти, подкачки, диска, контейнеров и портов.
3. Синхронизировать проверку готовности PostgreSQL с фактическими миграциями и правами; получить `healthy` без расширения прав сверх требуемых функций.
4. Только после этих двух PASS запускать Wave 1: развернуть шлюз Poruchik и серверное ядро задач с указанными лимитами.

## Ограничение доказательства

Средние показатели процессора и памяти основаны на короткой серии живых замеров. На сервере не было доступно отдельного архива `sar`; исторические средние Netdata не выгружались. Максимумы памяти взяты из счётчиков контрольных групп Linux с момента запуска контейнеров, а аварии памяти — из журнала ядра. Этих данных достаточно для запрета установки на текущие 1,6 ГиБ, но после расширения всё равно требуется повторный аудит и нагрузочная проверка пилотного потока.
