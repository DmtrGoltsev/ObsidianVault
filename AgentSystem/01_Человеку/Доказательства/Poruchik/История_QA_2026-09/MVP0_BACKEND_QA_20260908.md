## FCM и восстановление беседы

Первичная причина отказа FCM была в том, что Task Core находился только во внутренней сети Docker без внешнего маршрута. После добавления отдельной сети исходящих подключений был пересоздан только Task Core с тем же образом. Проверки DNS и TLS к FCM/OAuth прошли; внешние порты не добавлялись, старые записи DLQ не воспроизводились.

Контрольное событие `TASK_CHANGED` создало outbox `75d26fd0-a389-4e05-9d7e-25d2d4d694b0`. Доставка завершилась со статусом `DELIVERED` с первой попытки и идентификатором провайдера. На Android в фоне появилась нейтральная системная нотификация; переход из неё открыл точную карточку задачи. Полный путь FCM и deep link пройден.

Для проверки восстановления создана ровно одна новая беседа через подписанный служебный маршрут: беседа `f3beb55d-5392-4359-a648-27f18bb1366f`, запуск `1b00a395-82c3-45ee-9108-412082d4d9e7`, dispatch `58095513-3873-4311-b409-c91b70d09599`. Запуск завершился `SUCCEEDED`, версия 3, ответ `NO_REPLY`. После ручного запуска и ввода PIN Android выбрал эту беседу и показал терминальный результат.

## Выявленные дефекты и состояние исправлений

- После принятия поручения MEMBER имеет право чтения исходной задачи через `ACCEPTED` assignment: `can_read_task=true`, а серверный список возвращает одну задачу. Задача остаётся `PRIVATE`; отдельный `access_grant` для неё не требуется.
- В production change feed после первого принятия был только `ASSIGNMENT UPSERT` (sequence 114). Последний `TASK UPSERT` (sequence 107) появился до получения права, поэтому клиент уже прошёл эту позицию курсора и показал пустой список. Исправление `23ff88e` добавило авторитетный `TASK UPSERT` при `ACCEPT`; изолированный PostgreSQL-прогон прошёл 26/26 тестов без пропусков.
- После точечного выпуска Task Core `mvp0-assignment-sync-20260908-1005` свежая проверка прошла: назначение `32f66d1c-43ae-443f-829d-0dbaa187fc11` принято запуском `49f5275e-5427-4c74-8eb4-ff5e6c2f4a63`, а change feed после предварительного cursor 119 выдал `ASSIGNMENT` 120 → `TASK UPSERT` 121 → `CALENDAR_ITEM` 122. После одного общего обновления MEMBER увидел приватную задачу `MVP0 Sync Accept Regression 0809`.
- У нового MEMBER-устройства после штатного запуска и синхронизации не появилась серверная регистрация FCM. Это отдельный дефект регистрации токена; поручение и все 13 инструментов проверены в foreground независимо от него.
- Исправления экрана фокуса и отображения московского времени проверены на подписанном обновлении Android: сессия и PIN сохранены, задача видна в фокусе, срок `2026-09-08T15:30:00+03:00` отображается как `15:30`.
- Документный контур исправлен в `7d509f8` и миграции Flyway V9: валидный `root.md` принимается, traversal отклоняется стабильной доменной ошибкой, parent остаётся в пределах одной задачи, цикл запрещён, список имеет устойчивый depth-first порядок. Изолированная проверка root/child и трёх негативных случаев завершилась rollback без остатка. Актуальный полный прогон Task Core после следующих изменений — 31/31, без ошибок и пропусков.
- Гонки противоположных решений proposal и assignment детерминированно воспроизводились до исправления: оба вызова возвращали успех и могли создавать лишний аудит или побочный эффект. Коммиты `0d25c6e` и `68d6004` блокируют целевую строку `FOR UPDATE` до проверки терминального состояния и побочных эффектов. Production Task Core `poruchik-task-core:mvp0-decision-lock-20260909-1043`, image `sha256:91551487956011f30a79b209eebf33e71408db1d0624cf06fadf05ddf5bfe8a6`, Flyway V9, readiness `UP`, restart count 0. Live canary для обоих ресурсов дал ровно один HTTP 200, один типизированный 409, один терминальный статус и один набор аудита/побочных эффектов; push-регистраций и доставок в тестовом workspace не было.
- Локальные проверки маршрутизации, устаревших версий и push-состояний находятся в `561e6fc`. Ранее закрытая нейтральная доставка `TASK_CHANGED` и переход к точной задаче остаются действительными; расширенная проверка FCM на физическом телефоне пока частична.
- На физическом телефоне во временном Android-пользователе офлайн-задача сначала была видна локально, затем после остановки процесса и общего обновления исчезла. Серверная задача не появилась, а количество idempotency-записей не изменилось. Устройство `7419238c-402c-40b1-b741-1b3779d4a2ac` не было отозвано, но на момент ретроспективного снимка активных API-сессий было 0. Фактический ответ HTTP `401` для этого обновления не захвачен, поэтому потеря именно при остановке процесса, отказ refresh и иная причина пока не различены. Требуется пассивная диагностика в подписанной сборке; неподписанная QA-сборка на телефон не устанавливалась.
