# Poruchik — решения по RocketFlow

Главное решение: новое Android-приложение создаётся как отдельный продукт. RocketFlow используется как источник проверенных продуктовых принципов. Перенос кода возможен только после отдельного согласования владельца и технического аудита.

| Решение | Что относится |
|---|---|
| Переносим как продуктовый принцип | Папка → цель → задача, быстрый ввод, Фокус, календарь, сроки, связи, подзадачи, одно главное действие на экране |
| Переносим только после аудита и согласования | Изолированные серверные модели, проверенные правила дат, отдельные чистые компоненты интерфейса |
| Меняем | Ответственный и владелец задачи, передача части, производные задачи агента, постоянные входящие, права на ветку документов |
| Полностью перепроектируем | Авторизацию, сетевой слой, автономную синхронизацию, хранение токенов, push-уведомления, подтверждения, аудит, привязку Telegram |
| Не переносим | Старый Android-монолит, прямой доступ клиента к внутренним сервисам, устаревшее локальное хранение, неявные права |
| Откладываем | Публичный магазин, сложную аналитику нагрузки, совместный редактор Markdown, торговую площадку инструментов |

## Почему нельзя переносить приложение целиком

- Старая архитектура не рассчитана на OpenClaw и n8n как отдельные уровни ответственности.
- Требуется новая многопользовательская модель с личными задачами, скрытыми даже от владельца рабочей области.
- Автономная очередь должна предотвращать двойное выполнение.
- Задача и технический запуск агента должны быть разделены.
- Документация должна иметь отдельные права на ветку.
- Приглашения, привязка Telegram и подтверждения требуют новой модели безопасности.

## Условие переноса отдельной части

До переноса фиксируются:

1. конкретный модуль;
2. польза переноса по сравнению с новой реализацией;
3. зависимости;
4. результаты проверки безопасности;
5. стоимость адаптации;
6. решение владельца.
