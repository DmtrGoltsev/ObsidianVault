# Инвестиционные рекомендации Finance

## Назначение и границы

Finance хранит личные брокерские портфели пользователя и по явной кнопке формирует предложение по их изменению. Поддерживаемые источники снимков: Синара, СберИнвестиции и Финам. Ввод начинается со скриншотов брокерского приложения, после распознавания пользователь подтверждает извлечённые позиции и счёт. Сделки приложение не совершает: пользователь выполняет предложенные действия вручную.

Целевая структура риска: 40% консервативная, 30% умеренная и 30% агрессивная часть. Рекомендация учитывает российский рынок, несколько брокерских счетов одного владельца, свободные деньги и плановое ежемесячное пополнение. Результат не является индивидуальной инвестиционной рекомендацией.

## Пользовательский путь Android

1. Во вкладке «Активы» пользователь добавляет или продолжает черновик брокерского портфеля.
2. После подтверждения распознавания создаётся неизменяемый снимок портфеля, связанный с профилем счёта.
3. Экран показывает объединённую стоимость, число счетов и позиций, историю анализов и допущения отчёта.
4. Кнопка обновления рекомендаций создаёт одну асинхронную задачу. Пока задача выполняется, интерфейс показывает её состояние.
5. После готовности приходит нейтральное push-уведомление «Анализ портфеля готов». Deep link открывает конкретную рекомендацию; суммы и названия бумаг в push не передаются.
6. Если доставка запроса исчерпала попытки, пользователь может безопасно повторить доставку той же задачи. Новый анализ и новая задача при этом не создаются.

В debug-сборке разрешён явно отключённый push без `google-services.json`. Для production push необходима внешняя Firebase-конфигурация; ключи и service account в Git не хранятся.

## Backend и доставка

Основные сущности: импорт снимка, снимок портфеля, профиль брокерского счёта, задача рекомендации, отчёт, outbox-событие, push-устройство и запись доставки push.

Отдельный worker атомарно забирает outbox-событие, выдаёт аренду, восстанавливает просроченную аренду, применяет backoff и завершает событие только после подтверждённого приёма. Запрос в закрытый n8n/gateway подписывается HMAC по канонической строке из метода, пути, времени, nonce и точных байтов тела. Идентичность задачи, события и ключа идемпотентности сохраняется на всех повторах.

После максимального числа попыток связанная задача получает явное состояние ошибки доставки, чтобы интерфейс не оставался заблокированным. Авторизованный повтор возобновляет то же событие. Gateway хранит результат до подтверждённого callback и по тому же `eventId` не запускает DeepSeek повторно при потерянном ACK.

Готовый callback:

- проверяет владельца, подпись, nonce и допустимый узкий переход состояния;
- сохраняет один отчёт и канонический семантический хеш результата;
- гасит ожидающее или уже арендованное событие повторной доставки до следующего сетевого вызова worker;
- принимает идентичный повтор до изменчивых проверок свежести и политики;
- отклоняет отличающийся результат;
- для старой строки с пустым `callback_hash` сравнивает полный канонический результат и только после совпадения закрепляет хеш.

Канонизация считает одинаковыми один и тот же момент времени с разными часовыми поясами, равные `Decimal` с разным масштабом и перестановки порядконезависимых действий, агрегатов и источников.

## n8n, DeepSeek и рыночные данные

n8n `2.39.8` содержит тонкие неактивные workflow и передаёт запрос во внутренний gateway. Секреты DeepSeek, HMAC и шифрования очереди доступны gateway, но не workflow. Gateway получает данные из разрешённых доверенных источников, проверяет схему ответа модели и сохраняет callback до отправки backend.

Каталог MOEX обновляется worker раньше TTL, по умолчанию каждые 12 часов. Advisory/singleton lock не допускает параллельные одинаковые обновления; ручное обновление сохраняется. Внешние адреса и редиректы проходят закрытую сетевую проверку, а устаревшие рыночные данные приводят к отказу, а не к выдуманному результату.

FCM используется через HTTP v1 и OAuth2 service account из внешнего файла или переменной окружения. Регистрация устройства принадлежит пользователю и сессии; обновление токена, logout/revoke и удаление невалидного токена обрабатываются явно. Уникальность доставки по паре событие-устройство исключает дубли push.

Backend-зависимость `google-auth[requests]>=2.40,<3.0` объявлена в штатном `apps/backend/pyproject.toml`. Финальная локальная QA-проверка синхронизировала отдельное окружение той же командой, которую использует CI: `pip install -e "apps/backend[dev]" pyyaml`. После установки `google-auth 2.58.0` полный backend suite и три ранее падавших mocked FCM-кейса прошли. Это подтверждает локальный транспортный контракт, но не заменяет live-проверку с внешним Firebase-проектом.

## Непроверенные внешние контуры

Отдельного E2E требуют реальные скриншоты всех поддержанных брокеров, live DeepSeek, live FCM с внешним Firebase-проектом, Docker build/smoke и production. Отсутствие этих проверок не следует трактовать как подтверждение готовности внешних сервисов.

### Локальная попытка Docker от 2026-09-21

Docker Desktop `4.88.1` установлен, Docker CLI имеет версию `29.7.2` и API `1.55`. При скрытом штатном запуске backend Docker Desktop аварийно завершился на инициализации Ingest server: он не смог удалить `C:/Users/style/AppData/Local/Docker/run/sailor-ingest.sock` с сообщением `The file cannot be accessed by the system`.

После неответившей штатной команды остановки были завершены только процессы `Docker Desktop` и `com.docker.backend`, запущенные из каталога установленного Docker Desktop. После полной остановки их осталось `0`. Файл точно совпал с ожидаемым путём, имел размер `0`, атрибут `ReparsePoint` и дату 2026-08-29, но Windows не разрешила безопасно запросить reparse point или удалить файл. Сброс к заводским настройкам, удаление Docker data, images, volumes и повторный запуск не выполнялись.

Поэтому Docker build/smoke остаются заблокированными локальным состоянием Docker Desktop. Compose config по обоим контурам ранее прошёл без запуска daemon; неизвестная локальная и production БД не затрагивались.

### Live PostgreSQL без Docker от 2026-09-21

В Windows найден уже установленный PostgreSQL `18.3`. Без установки компонентов и без Windows service был создан временный кластер `finance-pg-qa-12ea2b1527ff47fc9c3419370037e7f3` в `%TEMP%`, слушавший только `127.0.0.1:58802` с `trust` внутри изолированного тестового кластера. Использованы отдельные базы `finance_qa`, `finance_fresh` и `gateway_qa`; существующий сервер на `5432` не затрагивался.

Чистый Alembic upgrade выявил дефект: ревизия `0021` пыталась расширить отсутствующую `outbox_events`. В commit `813449ecbb423ad5bc31b8862df4df915842b9fc` ревизия получила безопасное создание базовой outbox-таблицы при её отсутствии и сохранение уже существующей таблицы. После исправления новая база прошла всю цепочку до `20260921_0025`; создана одна `outbox_events` с шестью индексами.

Legacy report пережил реальный цикл `0024 -> 0025 -> 0024 -> 0025`: после первого upgrade `callback_hash` был `NULL`, после записи тестового хеша downgrade сохранил отчёт и удалил колонку, повторный upgrade сохранил отчёт и снова создал `callback_hash=NULL`.

Gateway schema проверена в отдельной базе. После остановки и повторного запуска PostgreSQL два новых процесса/соединения попытались повторить тот же `event_id` и ту же пару `job_id + attempt`: обе вставки дали `0`, а в таблице осталась одна неизменённая строка `ready`; две разные nonce сохранились. Это подтверждает durable dedupe на уровне PostgreSQL после рестарта.

Временный сервер штатно остановлен, `127.0.0.1:58802` перестал отвечать. После проверки абсолютного пути удалён только созданный каталог кластера с 2340 временными элементами; каталог больше не существует.
